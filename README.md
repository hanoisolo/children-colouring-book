# Children's Colouring Book

A personalised colouring book, generated in the browser. Type a theme and a
child's name, and the app draws a six-page A4 colouring book and hands it to you
as a PDF.

- **Theme** — `space dinosaurs`, `under the sea`, `fairy garden`, anything. The
  theme picks which motifs appear.
- **Name** — up to 20 characters. It goes on the cover, drawn as thick vector
  strokes a child can colour in.

No backend, no third-party libraries.

## Using it

**Download the app and open it.** It is one file. No install, no server, no
build step, no terminal:

<https://github.com/hanoisolo/children-colouring-book/releases/latest/download/colouring-book.html>

Save it anywhere and double-click it. It runs from disk, offline, in vector
mode. That is the app — everything below is for people working on it.

That link always serves the newest release. The file is also committed at
`dist/colouring-book.html` if you would rather read the source of what you are
running.

## Development

You do not need any of this to use the app.

**Running the source.** `index.html` loads `app.js` as an ES module, and a
browser refuses to fetch a module from a `file://` page because the origin is
opaque. So the source form needs a server:

```
npm start
```

Then open <http://localhost:8000>. `serve.js` is a small zero-dependency static
server that exists only to avoid that restriction, and the page says so instead
of failing silently. The single-file build has no such problem because the
bundler inlines every module into one classic script.

There is no `npm install`. `app.js` imports the rest of `src/` directly.

**Rebuilding the single file** after changing anything in `src/`, `app.js`,
`styles.css` or `index.html`:

```
npm run build
```

`build.js` inlines the stylesheet and all ten modules into one classic script.
It is not a general-purpose bundler; it handles this project's import graph and
nothing else. **The rebuild is a discipline, not a check** — no test can tell
that `dist/colouring-book.html` is stale, so a change to `src/` without a
rebuild ships a stale app.

**Cutting a release.** The download link above resolves to the newest release's
`colouring-book.html` asset, so a release is what publishes a new version:

```
npm run build
git add dist/colouring-book.html
git commit -m "Rebuild the bundle"
git push
```

Then create a release tagged `vX.Y.Z` with `dist/colouring-book.html` attached
as an asset. The asset must be the rebuilt file, not a copy from an earlier
release — the whole point of the link is that it serves what is on `master`.

## Two ways to draw the art

The app picks a pipeline at submit time, based on whether you supply an API key.

| | Vector (default) | Image |
| :--- | :--- | :--- |
| **Key needed** | no | yes |
| **Art** | procedural polylines from `src/motifs.js` | generated by Gemini |
| **Cost** | free | about $0.20 per book |
| **Same input, same output** | yes, byte-identical | no, fresh art each run |
| **Works offline** | yes | no |

Leave the key field empty and you get the vector book: instant, free, offline,
and identical every time. Paste a key and you get six generated illustrations
instead.

### Image mode

The model is **`gemini-3.1-flash-lite-image`** (Nano Banana 2 Lite), the
cheapest Gemini image model at **$0.0336 per image** — $30 per 1M image output
tokens, 1120 tokens per image. A book is six images, so **about $0.20**. The app
shows the estimate under the key field before you generate, and reports the
actual cost afterwards.

Get a key from <https://aistudio.google.com/apikey>. Paste it into the key
field. That is all.

Three things worth knowing:

- **The key is never stored.** It lives in the password field for the duration
  of the page and is sent only in the `x-goog-api-key` header. No
  `localStorage`, no cookie, no query string, no log. Reload and it is gone.
- **The name on the cover is still vector.** Image models misspell names, so the
  cover is a generated illustration with a white band across the top and the
  name drawn as thick strokes from `src/lettering.js`. The prompt reserves the
  top third of the frame so the band never covers the art.
- **Image mode is not deterministic.** The same theme and name give different
  art each run. That is the feature, not a bug. Vector mode remains
  byte-identical.

The browser calls the Gemini API directly, from your machine, with your key.
There is no proxy and no server of ours in the path.

## Running the tests

```
npm test
```

Two layers:

- `node test_colouring_book.js` — 267 tests, no dependencies. Runs offline in
  Node and covers the whole pipeline headlessly, calling the same functions the
  browser calls. Image mode is tested against a stubbed `fetch`, so the suite
  never reaches the network and never bills a key.
- `node test_browser.js` — 3 tests in headless Chromium: the vector path, the
  image path with a stubbed `fetch`, and `dist/colouring-book.html` loaded over
  `file://`. This is the layer that catches a page which does not work at all,
  which the unit suite cannot see.

The browser layer needs Edge or Chrome installed. It does not skip silently if
neither is found — it fails and tells you, because a browser test that quietly
does nothing is how a dead Generate button once shipped.

## How it works

Two strings go in; a `Uint8Array` PDF comes out. In vector mode everything
between is pure and deterministic, so the same theme and name always produce a
byte-identical book.

| Module | Role |
| :--- | :--- |
| `src/rng.js` | FNV-1a hash and a seeded PRNG. All randomness is derived from the inputs, never from the clock. |
| `src/themes.js` | Normalises the theme, strips stopwords, singularises plurals, and maps keywords onto a 25-motif vocabulary. Falls back to the full set when nothing matches. |
| `src/motifs.js` | 25 procedural generators — star, planet, rocket, moon, dinosaur, fish, shell, wave, flower, tree, butterfly, cloud, sun, house, balloon, cat, dog, car, mountain, rainbow, bird, boat, robot, cupcake, snowflake. Each emits polylines in a `0..1` box. |
| `src/lettering.js` | A single-stroke vector alphabet. Accented letters resolve by NFD decomposition into a base glyph plus accent strokes, so `Zoë` and `José` work. |
| `src/page.js` | Interior page composition: frame, ground line, and 3–7 motifs on a jittered grid that never overlap. Owns the SVG serialiser. |
| `src/cover.js` | Cover composition. The name is uppercased, fitted to at most four lines, and never shrinks below a 60 pt cap height. |
| `src/imagegen.js` | The Gemini image client: prompt construction, request building, response parsing, retries, and cost estimation. |
| `src/pdf.js` | A PDF 1.4 writer. Assembles the document as byte chunks so xref offsets come from real byte counts, not string lengths. Embeds JPEGs as `/DCTDecode` XObjects. |
| `src/book.js` | The orchestrator. Validates input, plans the pages, composes them, and refuses to return a book whose pages are not pairwise distinct. Owns both pipelines. |
| `app.js` | The DOM controller. Wiring only — every decision worth testing lives below it. |
| `build.js` | The bundler. Inlines the stylesheet and every module into `dist/colouring-book.html`. |

### The polyline IR

`src/page.js` and `src/cover.js` emit one intermediate representation: polylines
in top-down A4 user units, each carrying `closed`, `fill` and a stroke weight.
The SVG preview and the PDF both consume that same IR. The Y axis is flipped in
exactly one place, `src/pdf.js`, so the preview and the print cannot drift apart.

Image mode reuses the same IR for the cover overlay: the generated JPEG is one
XObject, and the white band plus the name are polylines drawn on top of it. One
`fitImageRect` places the image in both the PDF and the preview, so what you see
is what prints.

### Why the PDF writer is hand-rolled

Three details are easy to get wrong and all are load-bearing:

1. **Byte offsets.** The xref table stores the byte offset of every object.
   Mixing JS string lengths with multi-byte bytes shifts every subsequent
   offset, so the document is assembled as byte chunks and offsets accumulate
   from `chunk.length`.
2. **Fill colour.** PDF's default fill is black, so a `B` operator without an
   explicit `1 1 1 rg` paints a filled shape solid black. The fill colour is set
   to white once per page and never changed.
3. **The CTM.** `cm` mutates the graphics state, so an image placement without a
   surrounding `q`/`Q` leaks its transform into every later operator on the
   page. Every image is wrapped.

`B` also implicitly closes an open path, which would silently change the shape
of a `fill: true, closed: false` polyline. Both writers therefore close a path
whenever it is closed *or* filled.

## Constraints

- **Vector mode is deterministic:** no `Math.random()`, no `Date.now()`, no
  locale-dependent sorting. The same inputs give a byte-identical PDF. Image
  mode is deliberately not.
- Pure black strokes on white, at least 4 pt wide at A4 scale.
- No `eval`, no `new Function`, no dynamic `import()`.
- Zero dependencies. No test opens a browser, binds a port or makes a request,
  with one exception: `test_browser.js` drives headless Chromium against the
  real page. Image mode is tested against a stubbed `fetch`, never the live API.
- The API key is never persisted and never written into the PDF.
